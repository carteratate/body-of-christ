# HyDE passage generation: Haiku 4.5 or GPT-5.6 Luna?

Research checked September 18, 2026. Recommendation: **A/B first; keep Haiku 4.5 in production until retrieval quality and end-to-end latency are measured.** Luna's listwise-reranker win is not evidence that it writes better hypothetical corpus passages. The tasks use different prompts, outputs, and quality measures. Luna has a strong price case, but a provider switch also changes how reasoning tokens, completion limits, failures, and concurrency behave.

## What TheoCorpus actually does

- `HYDE_MODEL` defaults to `claude-haiku-4-5`; `RERANK_LUNA_MODEL` separately defaults to `gpt-5.6-luna`. Both are configurable, but [HyDE's call site](../../services/api/app/rag/steps/hyde_s25.py#L320-L351) is hard-wired to `anthropic.AsyncAnthropic.messages.create`, so setting `HYDE_MODEL=gpt-5.6-luna` alone would fail. See [config](../../services/api/app/config.py#L51-L57) and the [Luna reranker adapter](../../services/api/app/rag/steps/llm_rerank/openai_provider.py#L21-L91).
- The model writes source-style hypothetical passages, not answers shown to the user. The revised prompts generally ask for roughly 80–170 words, with a shorter 50–100-word canon-law provision. [Prompts](../../services/api/app/rag/steps/hyde_s25.py). The app embeds each result and uses it as a separate vector-retrieval path alongside the original query; passage wording and diversity can change which real chunks enter the reranker. [Generation and embedding](../../services/api/app/rag/steps/hyde_s25.py), [retrieval paths](../../services/api/app/rag/steps/retrieve_vector.py). This is consistent with the original [HyDE paper](https://arxiv.org/abs/2212.10496), which generates a hypothetical document then embeds it for retrieval.
- Ordinary Bible search makes one 50-token genre-selection request, then generates four passages. Focused Bible search skips selection and generates all eight prompts: free-form plus seven genres. A Bible-specific semaphore permits four simultaneous passage calls, so eight normally take two waves. Non-Bible collections each get one passage, spread across three key/client slots with a limit of three concurrent calls per slot. [HyDE run](../../services/api/app/rag/steps/hyde_s25.py), [client/semaphore assignment](../../services/api/app/rag/api_keys.py), [focused-path selection](../../services/api/app/rag/pipelines/runner.py). The generator uses a 45-second Anthropic client timeout. An individual failed passage is omitted, while query-vector search remains available. An invalid or failed genre-selection response falls back to four default genres. [Failure handling and fallback](../../services/api/app/rag/steps/hyde_s25.py), [query fallback](../../services/api/app/rag/steps/retrieve_vector.py).
- The [80-question round-three report](../eval/ROUND3_REPORT.md) found Cohere plus Luna listwise reranking better than Cohere plus Haiku listwise reranking by 0.019 mean judged score, with lower rerank latency in that run. **It held HyDE at Haiku for every pipeline.** The committed [result artifact](../eval/eval80-round3-final.jsonl) fingerprints the HyDE model as `claude-haiku-4-5`, and [shared capture](../../services/api/app/rag/compare/shared_runner.py#L79-L100) computes HyDE once before comparing rerankers. It cannot answer this HyDE question. It does offer a tested query set and methodology to adapt.

## Current provider facts

| | Claude Haiku 4.5 | GPT-5.6 Luna |
|---|---|---|
| API price, per 1M tokens | $1 input / $5 output | $0.20 input / $1.20 output |
| Context / maximum output | 200K / 64K tokens | 1,050,000 / 128K tokens |
| Thinking default relevant to these calls | Manual extended thinking is off unless requested | `reasoning.effort` defaults to `medium`; `none` is supported |
| Availability / limits | Active; organization limits depend on tier | Available via Chat Completions and Responses; model page gives tier-specific RPM/TPM |

Sources: Anthropic's [model overview](https://platform.claude.com/docs/en/models/overview), [Haiku thinking behavior](https://platform.claude.com/docs/en/models/sonnet-5/migration-guide), and [rate limits](https://platform.claude.com/docs/en/api/rate-limits); OpenAI's [Luna model page](https://developers.openai.com/api/docs/models/gpt-5.6-luna) and [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning). Both context windows dwarf these short prompts, so they are not a selection criterion. Anthropic calls Haiku its fastest current Claude model; OpenAI positions Luna for cost-sensitive high-volume work. Those are within-provider descriptions, not comparative latency measurements. [Anthropic overview](https://platform.claude.com/docs/en/models/overview), [OpenAI Luna page](https://developers.openai.com/api/docs/models/gpt-5.6-luna).

At equal token counts, Luna is 5× cheaper on input and about 4.2× cheaper on output. Illustrative arithmetic only: eight calls at 250 input and 220 generated output tokens each cost about $0.0108 on Haiku versus $0.00251 on Luna. The repo's current [cost tracker](../../services/api/app/rag/steps/cost_tracker.py) uses these same rates. Real savings depend on actual tokens, retries, and especially Luna's reasoning setting. OpenAI says invisible reasoning tokens are **billed as output** and consume the output limit; a completion can end before visible text appears. [OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning). A HyDE adapter should explicitly test `reasoning_effort="none"` and `low` rather than inherit Luna's medium default. `none` might reduce latency and cost but could weaken source voice or theological precision. That last point is a prediction, not a provider claim.

Luna supports Chat Completions, streaming, and structured outputs according to its [model page](https://developers.openai.com/api/docs/models/gpt-5.6-luna). The existing [Luna reranker adapter](../../services/api/app/rag/steps/llm_rerank/openai_provider.py#L45-L91) proves a Chat Completions path works in this codebase, but it is built around JSON scores, not free prose. Structured output could constrain genre selection to valid identifiers; it is not needed for the passage body and would add parsing. OpenAI's [structured-output guide](https://developers.openai.com/api/docs/guides/structured-outputs) documents strict JSON schema support. Provider rate limits are account/tier-specific. The [OpenAI model page](https://developers.openai.com/api/docs/models/gpt-5.6-luna) lists RPM and TPM by tier, while Anthropic's [rate-limit guide](https://platform.claude.com/docs/en/api/rate-limits) says to inspect the actual organization/workspace limits and warns about short bursts. The repo's multiple Anthropic keys are a local concurrency design, not evidence of extra organization-level quota.

## What would change, and what to test

Changing the env var is insufficient. A Luna HyDE implementation needs an OpenAI passage-generation adapter, explicit reasoning effort and output limit, client lifecycle/timeout and bounded concurrency, text extraction and finish-reason/refusal handling, usage accounting, and equivalent degradation events. It also needs a decision about whether the Bible selector migrates with generation. Moving both in one experiment would conflate selection errors with passage-writing quality; keeping Haiku selection initially isolates the generator. Existing OpenAI code supplies a pattern, but does not make this a one-line change. [HyDE implementation](../../services/api/app/rag/steps/hyde_s25.py#L320-L523), [Luna reranker](../../services/api/app/rag/steps/llm_rerank/openai_provider.py#L21-L91).

My suggested experiment is paired and offline. Freeze queries, corpus, embeddings, collection filters, retrieval `k`, and downstream reranking; generate Haiku and Luna passages independently for each query. Compare passage-validity checks (length, no headings, genre/source voice, duplicate/similar variants, theological red flags), then real retrieval outcomes: labeled relevant-chunk recall@k before reranking, best canonical-passage hit rate, final judged result quality, and per-collection differences. Record ordinary and focused Bible separately. Measure HyDE stage wall time and full search P50/P95, token usage including reasoning, 429s, timeouts, incomplete/refused responses, and fallback frequency. Run Luna `none` and `low` as separate arms; do not choose by token price alone. The current [evaluation methodology fingerprint](../../services/api/app/rag/compare/methodology.py#L20-L64) already records model IDs and fixed settings, but [shared retrieval capture](../../services/api/app/rag/compare/shared_runner.py#L79-L100) must stop sharing HyDE across the compared arms for this test. The current reranker judge scores final results, not labeled pre-rerank recall, so add or use independent relevance labels for that measure.

Decision rule: move only if Luna maintains or improves labeled recall and canonical-passage coverage, does not introduce meaningful genre/doctrinal regressions, and wins on measured end-to-end latency or cost without more degraded searches. A visible savings of a few mills per search is useful, but one missed source in a Catholic-theology search is a poor trade. Until that test exists, Haiku is the known-working generator and Luna's reranker result should remain a reranker result.
